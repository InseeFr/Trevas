# VTL provenance — overview & strategy

> Status: refining. This is the index/strategy document. The precise output
> contract and the golden test corpus live in
> [`20260728_02_provenance-output-and-tests.md`](./20260728_02_provenance-output-and-tests.md).

## Current state

`vtl-prov` extracts lineage from a VTL script + input datasets. Today this is done
by `ProvenanceListener`, an ANTLR `VtlBaseListener` driven by stateful flags
(`isInDatasetClause`, `rootAssignment`, `aggrGroupingClause`, …), followed by a
second `refineProgram` pass that **re-runs the engine** to attach component
types/roles and reconcile UUIDs via a static `idMappings` map.

Known problems with the current approach:

- Fragile: correctness depends on the order listener callbacks fire and on a web
  of boolean flags. Hard to reason about, hard to extend.
- Incomplete: only assignment, `calc`, `aggr`, `check_*`/ruleset, and dataset
  arithmetic are (partially) handled. `join`, `rename`, `pivot`/`unpivot`,
  user-defined operators are missing or shallow.
- Coarse: derivation edges are effectively **dataset → dataset**. Variable-level
  derivation exists as a class (`VariableInstance`) but is not wired to
  fine-grained `wasDerivedFrom` edges.
- `idMappings` is a `static` field → state leaks across runs.

There is also a second, parallel listener — `VariableGraphListener` — that already
builds a JGraphT `DefaultDirectedGraph<Variable, DefaultEdge>` with variable
*versioning* (`Variable.newVersion()`). It is the right instinct (a real graph,
versioned nodes) but limited: variable-only, a single **untyped** edge, still
listener-driven. The refactor generalizes it into a **typed** graph IR
(decision 2) and supersedes both listeners.

## Goal

Redefine provenance **output-first**: pin down exactly what graph we produce for
each VTL operation, encode it as a golden test corpus, and only then choose an
implementation that reproduces it. Cover as much VTL syntax as possible and drop
the hand-tuned listener flags in favour of a systematic pattern.

## Decisions (this round)

1. **Granularity: variable-level, grouped by dataset.** The primary contract is
   variable-to-variable lineage: each output `VariableInstance` records which
   input `VariableInstance`s (and which operation) produced it. Each
   `VariableInstance` is scoped to its `DataframeInstance`
   (`ds_sum.var1` ≠ `ds1.var1`), so "group by dataset" falls out of
   `DataframeInstance hasVariableInstance VariableInstance`. Dataset-level
   `wasDerivedFrom` edges are kept but become **derivable** from the variable
   edges (see output spec for the aggregation rule).

2. **A schemaless expression-dependency graph, not RDF-as-golden.** The primary
   artifact is a **directed property graph** (backed by **JGraphT**, already a
   `vtl-prov` dependency) that mirrors the program's **resolved expression tree**,
   with names resolved across statements. Generic nodes (a dataset instance, a
   variable instance, **or an expression**) with a free-form property map, and
   edges expressing **one relation — `dependsOn`** ("computed or selected from") —
   with optional annotations (`op`, `role`). Node kinds, roles, types, membership,
   operator identity are all **properties**. This matches the original goal ("a
   complete Java object containing all the information") and the existing
   `VariableGraphListener` (a plain `DefaultDirectedGraph`). RDF/SDTH is one
   **downstream conversion**, not the source of truth.

3. **One uniform rule — no producer/scalar dichotomy.** An entity `dependsOn`
   whatever it is computed or selected from. This covers dataset operators,
   columns, *and* scalar expressions identically. A `filter` predicate is an
   expression node like any other, so selectors are **represented**
   (`dependsOn … role=condition`), not dropped. Expressions are named at
   reference-level (one node per whole expression); full-AST depth is the same
   model deeper, deferred. Operator-level typing, statement grouping, dataset-only
   lineage, SDTH/RDF — all are conversions over this graph. "The IR can always be
   improved or converted" (KISS).

4. **Golden format: a flat, sorted "fact list"** — one `subject predicate object`
   line per node-property and per edge (de-RDF'd N-Triples with short local ids).
   Predicates are `a` / property keys / `dependsOn`. Hand-writable, line-diffable,
   greppable, and a near find-replace from the RDF conversion (`role`-value
   `dependsOn` → `prov:wasDerivedFrom`, `role=condition` → `prov:used`). Assertion
   is set-equality over lines (ids deterministic, no isomorphism). An optional
   generated DOT render is review-only.

5. **Fidelity is kept by nodes+properties, not a schema.** The two transformations
   in `ds[filter …][calc …]` are two `dependsOn` hops (annotated `op: filter` /
   `op: calc`) through an anonymous intermediate; the predicate `mod(var1,2)=0` is
   its own expression node the intermediate `dependsOn (role=condition)`.

## Non-goals (this round)

- Choosing the final implementation mechanism (listener vs visitor vs engine
  hook). Captured below as open options; decided only after the corpus exists.
- RDF serving / Trifid / Kubernetes deployment.
- Row-level ("cell") provenance. Filter/where predicates influence *rows*, not
  specific output columns — we record predicate variables at step level, not as
  per-variable derivation edges. See output spec §Filter.

## Implementation options (deferred — do not pick yet)

The corpus is the acceptance test; any of these must reproduce it.

- **Listener (current).** Complex, fragile, but no engine changes.
- **Visitor over the parse tree.** Same coverage burden; special-casing
  function operators is awkward.
- **Navigable `VtlExpression`s.** Add provenance by walking the resolved
  expression tree instead of the raw parse tree — gives types/roles for free but
  ripples through the engine unless done with non-navigable default ctors.
- **Engine hook.** Observe assignments/operators as the engine resolves them.
  Simple in principle, unknown in practice.
- **DataStructure add-on graph.** Attach role/type metadata as a side graph.

The most promising direction is to derive provenance from the **resolved
expression tree** (types/roles known, no re-run), but that is a follow-up spec
once the corpus locks the expected output.

## VTL operations the corpus must cover

Tracked in detail (with expected variable-level rules) in the output-and-tests
spec. Checklist:

- [ ] assignment `:=` (temporary) and persistent `<-`
- [ ] dataset arithmetic (`ds1 + ds2`, scalar `ds * 3`)
- [ ] dataset-level scalar/unary fns (`abs(ds)`, boolean, comparisons)
- [ ] `calc`
- [ ] `filter` / `where`
- [ ] `keep` / `drop` / `ds#comp` (projection)
- [ ] `rename`
- [ ] `sub`
- [ ] `aggr` + `group by`
- [ ] analytic `over(partition by … order by …)`
- [ ] `join` (`inner_join`, `left_join`, `using`)
- [ ] set operators (`union`, `intersect`, `setdiff`, `symdiff`)
- [ ] `pivot` / `unpivot` (determinism caveat)
- [ ] `check` / `check_datapoint` / `check_hierarchy` + ruleset `define`
- [ ] user-defined operators (`define operator …`)

## Open questions

- **Dataframe instance identity.** When a name is reassigned (`ds <- ds[...]`),
  is the result a new `DataframeInstance` (version) or the same one mutated?
  Proposed: one instance per (label, defining step). Needs confirmation.
- **Filter/where predicate variables.** Record only as `usesVariable` on the
  step (proposed), or also as derivation on every pass-through output variable?
- **User-defined operators.** Black-box (operator = one activity,
  inputs→outputs) first, inline the body's variable lineage later?
- **Pivot/unpivot determinism.** Output columns depend on data values; how do we
  keep golden `.ttl` stable? (Fixed tiny inputs + sorted serialization.)
